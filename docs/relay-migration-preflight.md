# Inactive combined CORE storage migration preflight

The preflight and its declarative catalog are internal preparation modules. **No production module imports them, and no route, account allocator, alarm or guard is activated.** A `reviewable` calculation only says that the conservative model fits supplied observations. It does not establish current headroom, reserve live quota, authorize a deployment or protect a Worker that has already entered a schema helper. Production admission remains blocked until separately reviewed pre-DDL routing and a durable finite account allocator exist.

## Construction catalog

The declarative catalog records every native SQL definition: **36 application tables, 20 named indexes and 20 private job-change triggers**, plus exact managed `_cf_KV` and `sqlite_sequence` provider definitions. All 26 retained application-table definitions are unchanged from c4. Autoindexes are accepted only for a listed table. An unlisted table, index, trigger, view, or an altered listed definition blocks the inventory. Optional tables are positively observed absent or scanned; unknown schemas never receive zero-row credit.

All these application SQL entry points use the existing canonical **`jarvis-shared-v2` Hub** under `HUBS`. A new empty instance and an existing instance of that identity both need admission. The lightweight Hub constructor does not establish a barrier: public shared reads/writes/result/changes and import-hint paths enter schema helpers, owner handling enters `sharedSchema()` before `relayOwnerStore()`, Relay RPC enters shared/event/owner schemas, OAuth enters `relayOAuthStore()`, and alarms enter wake/publication/event helpers. Future admission must precede every relevant first access and ordinary-traffic mutation.

The fixed legacy public-key hash inbox, `oauth-registry`, responder-hash Hubs and token-workspace Hubs retain their existing KV paths. They do not receive new application SQL DDL, but their KV/database storage and all other account activity still belong in an explicitly enforced ordinary-traffic/account reserve. The helper recognizes the managed KV table without fetching its payloads or treating an unmeasured KV workload as free. Legacy page transfer sizes, CPU, network, Worker requests and KV billing are separate activation-review concerns.

Existing owner authentication cannot be used as an excuse to call owner/shared schema before admission. A future caller must preserve the current policy while admitting its initial existing-table authentication lookup and every denial **before any candidate DDL**. The helper supplies no such route, policy change or authentication adapter. Scope declarations cover only the explicitly provisioned affected inventory, not proof that an undeclared Hub or account workload does not exist.

## Owner evidence

Use the existing dashboard session; this path does not need a SQL console, CLI login, new credential, additional service, scope or grant. Provide visible plan/account usage and finite allowance or approved rollout limits for SQL rows read, rows written and stored bytes. Also include the fixed Hub/HUBS namespace header, its same-window read/write usage and stored bytes, the range selector and capture time. Do not include message bodies, callback URLs, identifiers, secrets or source cardinalities in public analytics or logs.

For October 9, 2026, the window must start **00:00 UTC and end at capture**. A GMT−3 UI therefore starts **October 8 at 21:00**. A partial screenshot with hidden resource/range headers and an axis spanning two local dates is insufficient. Use conservative displayed-usage upper bounds, including rounding uncertainty. Unknown plan, account/day usage, affected scope, storage, live schema or allocation stays blocked. An explicit observed zero differs from missing evidence. Paid finite rollout limits are operator-approved budget inputs, not a claim that a monthly allowance resets daily.

`evidence` requires `plan` (`workers-free` or `workers-paid`), `utcDay`, `windowStart`, `capturedAt`, account `{rowsRead,rowsWritten,storedBytes}` each `{used,limit}`, namespace `{binding:'HUBS',rowsRead,rowsWritten,storedBytes}`, and `perObjectStoredBytesLimit`. Times are UTC epoch milliseconds. The namespace and account must describe the same window. Capture older than five minutes, future capture, a shifted UTC boundary, inconsistent totals or unknown limits block before accessing source storage.

## Staged preparation and rollback

1. Independently review the exact desired source and pre-DDL routing. Provision a finite account plan and every affected internal scope outside the source SQL store. Labels are private operator-chosen identifiers; no public diagnostics are added.
2. Pre-reserve all declared scope allocations, ordinary traffic and finite external coordination/rejection overhead. `reserve` has `{rowsRead,rowsWritten,storedBytes}`; minima of 10,000 reads, 1,000 writes and 1 MiB are positive floors, not measured ordinary traffic. The real reserve must cover other Hubs/account traffic, source-monitor amplification, authentication/rejection and new upstream work. A future caller must enforce its finite allowance rather than merely supply a number.
3. Input is exactly `{action,runId,scope,expectedRevision,batchSize,evidence,reserve,allocations,coordination}`. Actions are `start`, `continue`, `report`, `discard`; a start has `expectedRevision:null`. At most sixteen scopes are declared. Each allocation has `{scope,rowsRead,rowsWritten,storedBytes}`. `batchSize` is 1–250. Each invocation prepays 2,000 SQL reads and 64 writes; the scope reserves at least 1 MiB for checkpoint footprint.
4. Call `await relayMigrationPreflightAdmission(ctx,input,now,reserveAdapter)` and pass only its one-use opaque permit to `relayMigrationPreflightStep(ctx,input,now,permit)`. Missing/forged/replayed/expired permits and invalid evidence do not access source storage. The complete input is snapshotted before awaiting the adapter; the request and its nested reservation references are frozen. A changed input cannot obtain a scope-B permit from a scope-A receipt.
5. The helper creates only its tiny attempt/checkpoint/source-revision tables and additive mutation monitors. Monitors are installed for at most eight source tables per step. `catalogInstallation.bootstrapPending` explicitly reports incomplete installation; no source counts are accepted as complete then. Source fences are captured only after all present sources have durable monitors, so writes before a monitor exists are included by the later fence.
6. Scan existing tables by rowid/integer key, `NOT INDEXED`, in at most 250 rows total per invocation. The bounded SQL catalog read has `LIMIT 256` and rejects saturation. Projections return row keys and scalar sizes/count flags, never message text, identity/token/credential values, callback configuration or JSON payloads. No target index, filtered full-history scan, `COUNT(*)`, or all-history write is performed. Sparse keys are fences, not cardinalities. Native cursor reads/writes and `sql.databaseSize` are measured.
7. Continue with the returned checkpoint revision and a fresh reservation. A lost response is recovered with `report`; stale revision does not advance it. An interrupted inventory page rolls back. External reservations commit before the permit; the tiny SQL attempt ledger commits before the inventory transaction. Lost receipts, lost step replies, rollbacks, reload, discard and restart remain prepaid.
8. Every insert/update/delete on monitored application tables invalidates source evidence, including equal-cardinality content edits. Changed or removed schema monitors invalidate it too. The helper does not stop old workers; old positional inserts remain valid and simply invalidate the scan. Stable intervals are needed to finish. Continuous writers can exhaust the finite plan and must not cause unlimited automatic restarts.
9. Discard with the current revision. Full-catalog teardown is itself checkpointed: `catalogInstallation.discardPending` reports progress, and `continue` resumes it. Native `DROP TRIGGER` bills catalog reads, so teardown chooses a bounded page from current catalog size rather than dropping all 108 monitors at once. Interruptions roll back that page. Only helper monitors/checkpoint/source markers are removed; application definitions, data, auth state and private history remain. The spent attempt ledger survives discard.
10. Gather complete reports no older than 30 seconds for every declared scope. `relayMigrationPreflightBudget()` adds full construction, catalog creation, OAuth/owner startup, public/receipt backfill, private cold feed/history/deadlines, conservative pending replay exposure, full daily legacy lane, complete preflight allocations, ordinary traffic and external coordination reserve. CORE uses keyed named-predecessor and artifact-revision lookups. The model retains a deliberately generous history term for one inventory-sized pending/conflict/recovery cycle. Repeated dependency polling, future upstream imports and unrelated traffic require a separately enforced external reserve; daily/page caps alone do not prove an aggregate SQL cost bound. Missing/stale reports, changed plans, UTC rollover and insufficient account/object headroom block.
11. A fitting aggregate remains a review packet. Before candidate DDL a separately reviewed caller must revalidate live catalog/revisions and fresh quota evidence, atomically reserve the aggregate migration remainder plus already prepaid work, and enforce all concurrent traffic/admission bounds. This helper neither performs that final reservation nor automatically starts migration. Any future source change requires a refreshed manifest/model and native qualification.

V3 does not resume V1/V2 reports or reinterpret their incomplete catalog. Old helper metadata must be cleaned up using its matching old helper under a finite reviewed invocation, or a separately reviewed metadata-only migration. A SQL attempt ledger binds the account allocation signature and does not permit a changed plan to reclaim spent usage. No metadata upgrade or plan-reset path is activated here.

## Required finite external account contract

`coordination` is exactly `{planId,maxReservations,maxRejections,rowsRead,rowsWritten,storedBytes}`. Counts and resources are finite nonnegative safe integers; reservations are positive and storage is at least 1 MiB. Read/write reserves must be at least `maxReservations+maxRejections`. That positive floor is only input validation: an actual adapter may cost more and must provide an independently qualified conservative bound. Changing the account plan or restarting an isolate does not replenish either counter.

The supplied `reserveAdapter(request)` must atomically and durably debit the approved account/scope envelope **outside source SQL before replying**. It must pre-provision the complete preparation reservation, coordinate all scopes, bind the reviewed plan/signature and UTC day, and reject unknown or lost state instead of recreating usage as zero. Its own coordinator, authentication, failure/rejection and restart overhead must fit the explicitly reserved finite budget. At cap, an independently enforced gate must reject before another charged SQL/storage probe. Infinite anonymous polling through a SQL-backed denial check violates the contract. This module does not provide that gate or durable allocator.

Requests contain `planRevision`, `reservationId`, `utcDay`, `scope`, `allocationSignature`, `allocation`, `envelope`, `accountPlanSignature`, `coordination` and `accountReserved`. `accountReserved` is the sum of all scope allocations, ordinary traffic and coordination; it covers preparation. Construction is unknown until inventory completes and needs its separately reviewed final aggregate reservation before DDL.

A success receipt is exactly `{status:'reserved',reservationId,utcDay,scope,allocationSignature,attempt,reserved,coordination}`. The scope `attempt` is positive and monotonic; `reserved` is exactly `{rowsRead:attempt*2000,rowsWritten:attempt*64,storedBytes:1048576}` within its allocation. Receipt `coordination` is exactly `{planId,signature,reservations,rejections,reserved}`: the account signature matches the frozen request, global reservations are at least the scope attempt and no greater than `maxReservations`, rejections do not exceed `maxRejections`, and the preparation reserve matches the request. Receipts and charged reports expose the internal reservation proof; they are not public output.

An adapter may return exactly `{status:'blocked',reason}` for `preflight_allocation_exhausted`, `preflight_allocation_plan_changed`, `external_admission_unknown`, `external_rejection_budget_exhausted` or `external_account_budget_exhausted`. Failed/lost replies remain spent and block source SQL. Warm contexts cache known caps; a cold context requires the external durable gate. An arbitrary callback claiming durable persistence is not evidence of it. Unknown external state, absent final reservation, undeclared workload or unreviewed ingress therefore remains an activation blocker even if a fictional fixture is green.

Permits bind the native context and unchanged input, cannot pass through JSON or survive reload, expire after 30 seconds and are consumed by rejected use. All admitted SQL attempts, including report/discard and obsolete checks, are prepaid. Valid external admission does not grant owner/session authorization; the future caller must preserve current checks and never expose private counts on public routes or caches.

Ordinary traffic may cost much more than its input floor. Live plan/evidence, exact ingress/source coverage, durable finite allocator/rejection admission, traffic enforcement, CPU/network/KV/Worker billing, source stability and the final aggregate reservation remain necessary before activation. Public UI redesign, new scopes/grants/credentials/services and schedules are outside this change.
