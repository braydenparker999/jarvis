# Inactive Relay storage migration preflight

This is a local, reviewable preparation path. `backend/relay-migration-preflight.js` is exported but **nothing imports or routes it in production**. It does not install a production guard, approve a deployment, query account analytics, create the candidate indexes, migrate messages, issue credentials, change grants, or change alarms. A new Worker would need separately reviewed routing that invokes the preflight before every relevant schema entry point. Existing deployment holds remain in force.

The audit pins live source `c4d62409a3b67e4e5dac88809c6a4a0290b6e39e` and qualified main candidate `ea9c09c1ddb172c1f0d668b58a5e7066f1c8318f`. The follow-up `8fb73ad115c53e904844d3d5643c3fd9911370f8` changes tests/docs above live, not the live storage construction path. The model adds an explicitly labeled conservative reserve for the reviewed private job-feed follow-up; that reserve does not change the candidate source pin. CORE's newer expression index is intentionally outside this c4→ea9 target. A broader combined candidate requires a new manifest/source review before this can guard it; the private-feed reserve is not coverage for an unlisted index.

## Construction paths

| Candidate construction | Retained input | Live c4 behavior | Candidate ea9 trigger |
| --- | --- | --- | --- |
| `shared_kind_seq` | `shared_entries` | No kind/sequence index | `sharedSchema()` |
| `imported_comments_status` | `imported_comments` | Primary comment key only | `publicationSchema()` after `sharedSchema()` |
| `relay_event_created_seq` | `relay_events` | Primary/unique event keys only | `relayEventSchema()` |
| `relay_outbox_event` | `relay_outbox` | Primary key and due index | `relayEventSchema()` |
| Partial `relay_outbox_unsettled` | Entire outbox scanned; pending/failed rows indexed | No unsettled index | `relayEventSchema()` |
| `relay_oauth_expiry` | `relay_oauth` in the same Hub | Primary registry key only | `relayOAuthStore()` |
| `relay_oauth_category_expiry` | `relay_oauth` in the same Hub | No category/expiry index | `relayOAuthStore()` |
| Legacy OAuth client expiry extension and expired-row cleanup | Retained registry rows, conservatively including all rows | Already possible without these indexes | Both versions' first `relayOAuthStore()` access; ea9 also updates the new indexes |
| New public coordination/change tables and their indexes | Initially empty tables | Absent | `coordinationSchema()` called inside `sharedSchema()` |
| Public change backfill | All retained `shared_entries` | Absent | ea9 eagerly runs `INSERT ... SELECT` on first schema access |
| Delivered receipt backfill | Retained delivered outbox rows if the marker is absent | Already possible in c4 | Both versions' `relayEventSchema()` |

The Hub constructor is lightweight. That does not protect first access: the owner Hub branch calls `sharedSchema()` before `relayOwnerStore()`, Relay RPC calls shared/event schemas, shared/publication paths call their schema helpers, the registry path calls `relayOAuthStore()`, and an existing outbox alarm can call `relayEventSchema()`. A future guard must precede all of those paths, including the ordinary public request that first touches the migrated Hub. Importing this helper or running it after schema access provides no protection against index construction already incurred.

## Evidence the existing owner can supply

Use the existing Cloudflare dashboard session. No SQL console, remote table-count query, CLI login, API token, credential, additional scope, or grant is needed for the evidence handoff. Do not include message bodies, callback URLs, secrets, or private request identifiers.

Supply visible dashboard headers and the plan, account usage/allowances for SQL rows read, rows written, and SQL stored bytes, plus the fixed Hub/HUBS namespace header and that namespace's read/write/storage usage. Use a custom current-day window from **October 9, 2026 00:00 UTC to capture time**. In a GMT−3 dashboard axis, the start is **October 8 at 21:00**. Include the range selector and capture time; an axis crossing two dates with hidden resource/range headers cannot establish UTC-today headroom or identify the affected namespace. A previous partial screenshot supplies no usable quota evidence for this helper.

Use explicit finite limits and conservative usage upper bounds, including display-rounding uncertainty. On Paid, the finite limits in this input are an existing-owner-approved daily rollout budget, not a claim that the plan's monthly allowance resets daily. The helper is not a billing calculator. Unknown plan, quota usage, limit, scope, storage, or paid rollout budget stays blocked. Explicit dashboard zero is distinct from missing evidence; missing values never become zero. The existing owner supplies the per-object storage limit appropriate to the verified plan.

`evidence` requires `plan` (`workers-free` or `workers-paid`), `utcDay`, `windowStart`, `capturedAt` (UTC epoch milliseconds), account `{rowsRead, rowsWritten, storedBytes}` each `{used, limit}`, namespace `{binding:'HUBS', rowsRead, rowsWritten, storedBytes}`, and `perObjectStoredBytesLimit`. Account and namespace observations must cover the same stated UTC window. Evidence older than five minutes, a future capture, a shifted day boundary, or inconsistent namespace/account totals blocks before SQL.

## Staged preparation

1. Separately review the future pre-DDL routing against the exact desired source. Preserve existing authorization; do not expose counts on public endpoints or logs. Every affected Hub must have an operator-chosen internal label and an explicit allocation in one account-wide plan. Cover the legacy Hub if a new path can initialize schema there. Declaring one Hub is not proof that it is the whole affected inventory.
2. Reserve the sum of all declared preflight allocations plus a positive ordinary-traffic reserve against the supplied account evidence. Reserve rows read, rows written, and storage independently. Account for all other account/namespace activity; the helper does not discover it. Existing traffic also incurs the additive source-monitor writes while a preflight is installed. A production caller must coordinate this reservation; independent Hubs cannot each spend the same remaining account quota.
3. Prepare input with action `start`, a private run/scope label, `expectedRevision:null`, and `batchSize` from 1 to 250. The other input fields are `evidence`, `reserve`, and `allocations`. Each allocation is `{scope,rowsRead,rowsWritten,storedBytes}`. First call `await relayMigrationPreflightAdmission(ctx, input, now, externallyReviewedReserve)`. Only its opaque one-use permit can enter `relayMigrationPreflightStep(ctx, input, now, permit)`. There is no production reservation adapter in this change: missing admission is blocked before even accessing native storage. The external contract below is mandatory for every SQL call, including `report` and `discard`. Minimum invocation reservations are 2,000 reads and 64 writes, with 1 MiB reserved for the tiny checkpoint footprint. Ordinary-traffic reserve minima are 10,000 reads, 1,000 writes, and 1 MiB; those floors do not estimate actual traffic, which can require a larger owner-supplied reserve.
4. Only the helper's empty private metadata tables and additive revision triggers are created. Existing tables are scanned by their current rowid/integer key, `NOT INDEXED`, in at most 250 rows total per invocation. There is no `COUNT(*)`, filtered history scan, target index creation, payload transfer, or all-history write. Sparse comment IDs are fences, not counts. Native cursor counters and `sql.databaseSize` are measured. The unchanged source projections return keys or scalar count/size flags, never message text.
5. Continue with the returned checkpoint revision and a newly reserved permit. A lost response can be recovered with action `report`; a duplicate old revision cannot advance the checkpoint. Native scan/checkpoint failure rolls back that page. The external reservation commits before a permit exists, and the tiny SQL attempt ledger commits before scanning. Lost admission replies, lost SQL responses, stale admitted revisions, rollback, reload, discard, and restart cannot reclaim their prepaid envelopes. Admitted failures report measured native costs and cumulative reservation. The same still-fresh storage observation permits the explicitly allocated checkpoint growth; it does not require a screenshot after every page.
6. Any insert, delete, or update on a scanned source, including an equal-cardinality body or registry-value update, invalidates the evidence. Changed/removed schema guards invalidate it too. Discard with the exact current revision removes only the helper's source monitors/checkpoint; source data, existing indexes, credentials and contracts remain untouched. Start a new run after drift. The daily attempt ledger remains, so restarting cannot reclaim spent allocation. Exhaustion blocks before any source SQL; repeated denied calls do not read the SQL attempt ledger. A new UTC day requires new account evidence and an explicitly provisioned external allocation.
7. Gather complete fresh reports for every declared affected Hub and call `relayMigrationPreflightBudget(reports, options, now)`. Reports older than 30 seconds, missing Hubs, incomplete scans, mismatched plans or insufficient account/object headroom block. The calculation adds index construction, complete public/receipt backfill, retained private lifecycle/deadline history, a conservative private-feed reserve, pending publication replay, full preflight allocations, and ordinary traffic. It retains ea9's potential quadratic correction-history reads instead of assuming constant replay cost.
8. A `reviewable` result means only that the modeled aggregate fits the observed inputs. It neither reserves live account quota nor authorizes index DDL/deployment. Immediately before any future migration, revalidate source revisions and fresh quota evidence, enforce the externally coordinated reservation, and review the exact source model. Existing unbounded ea9 backfill is not made incremental by this helper; the separately reviewed bounded backfill implementation must still be selected. There is no background loop or automatic activation here.

This conservative version needs a stable source interval to finish. Continuous writers can force restarts; the helper does not stop traffic. A future routing review must address admission of source writes during the finite inventory pass and preserve older-worker compatibility. Source changes cannot be silently credited as an unchanged snapshot.

## Required external admission contract

The supplied internal `reserve(request)` operation must atomically and durably debit a finite approved account/scope envelope **outside the source SQL store before replying**. Its key is the approved account plan, UTC day and scope; run IDs, object restarts, duplicate requests and discarded inventory must not reset it. It must reject unknown reservation state, never reconstruct unknown spent usage as zero, coordinate all affected Hubs, and separately reserve a finite bound for its own coordination and rejection overhead. A denial must not start another uncharged SQL read. A production adapter that queries SQL for every rejected attempt would reproduce the reviewed defect and does not satisfy this contract.

The request contains `planRevision`, a fresh `reservationId`, `utcDay`, `scope`, `allocationSignature`, the scope allocation and the per-call envelope. A successful receipt must be exactly `{status:'reserved',reservationId,utcDay,scope,allocationSignature,attempt,reserved}`. `attempt` is a positive monotonic daily scope counter; `reserved` is exactly `{rowsRead:attempt*2000,rowsWritten:attempt*64,storedBytes:1048576}` within the finite allocation. The callback may instead return exactly `{status:'blocked',reason}` with reason `preflight_allocation_exhausted`, `preflight_allocation_plan_changed` or `external_admission_unknown`. Failed or lost replies block source SQL and remain spent in the external ledger. A live context rejects a non-increasing receipt before SQL and avoids another callback once its known finite allocation is exhausted. Across context/isolate restart, the durable external allocator remains mandatory; the SQL ledger also rejects a non-increasing admitted counter, with that admitted check prepaid and measured.

The helper binds the receipt to the fresh request nonce and the permit to the native context identity and the complete unchanged input. Permits cannot be supplied through JSON, copied, reused or carried across object/isolate reload; they expire after 30 seconds and a rejected use consumes the permit. A new report request requires a new reservation. No production callback, account allocator, rejection admission route or credential is supplied here. An arbitrary callback claiming persistence is not independent evidence of persistence: its implementation and finite denial budget must be reviewed before any wiring. Without that independently established contract, this remains blocked preparation, not live readiness.

Plan revision v2 invalidates v1 reports and checkpoints, whose manifest omitted the retained OAuth table. Do not resume or reinterpret v1 inventory as zero OAuth rows. Any existing local v1 checkpoint must be explicitly discarded through its matching old helper under a finite externally reserved invocation, or removed through a separately reviewed metadata-only migration; source tables and index definitions must remain untouched. No such migration is activated by this module.

## Local native evidence and limits

The fictional workerd regression seeds 5,000 rows each in public entries, imported comments, retained events, retained outbox, and private requests. One hundred pages inspect exactly 25,000 source rows before the candidate indexes; the test measures actual native reads/writes and database bytes, then constructs candidate schemas and lazily materializes private jobs through the existing paginated job list. The three helper files also pass all 13 regressions when transplanted alone onto accepted main `408ad5d9980d857c06a26e85108fd8da38961de7` under qualified Node 22 and 24; the fixture requires no private change-feed API. Separate fixtures seed 10,000 retained OAuth rows before both registry indexes, including a legacy-client population. Each OAuth inventory consumes 40 pages and measures 10,566 reads / 92 writes. Ordinary retained registry construction then measures 40,169 reads / 20,002 writes; first access with 5,000 legacy clients measures 60,171 reads / 40,002 writes. The aggregate OAuth migration reserve is 162,304 reads / 200,704 writes, including fixed schema overhead and a separately labeled legacy maintenance pass. Index construction reserves four reads and two writes per scanned/indexed row plus bounded metadata overhead; scalar category-byte lengths bound storage without returning keys or identity payloads.

The external admission fixture is explicitly provisioned in the fictional test host, outside native SQL, and survives object reinstantiation. It models the required contract, not production durable account coordination or isolate-restart persistence. Native tests cover concurrent admissions, forged/missing/replayed permits, twenty repeated exhausted denials across object reload with zero SQL reads/writes, unknown external state, and lost admission/SQL responses. The original dense-history, old positional-insert, equal-cardinality update, removed-guard, rollback, allocation, reload/discard, multi-Hub, report-expiry, midnight and quota assertions remain. External egress is prohibited.

This is neither a live table-count observation nor a proof that every arbitrary future workload fits these coefficients. The fixtures check generous bounds on the qualified construction path and represented retained histories. Account activity after capture, new upstream publications, CPU time, concurrency across Hubs, additional indexes, unusually corrupted legacy data, deployment source attestation, and live plan/account limits require independent review. Production data and source/cardinality reports must remain in existing authenticated owner/internal handling, with aggregate decisions kept out of public analytics/logs.
