Local read-amplification repair candidate

This focused candidate is based on the frozen public coordination plus owner-tool compatibility rehearsal. It does not attribute the reported account-level Durable Objects rows_read warning to Jarvis or a specific namespace. It changes no browser UI, polling cadence, responder schedules, subscriptions, credentials, grants, release gates or deployment pin.

Schema initialization is separated from state retrieval in the publication importer, owner storage and MCP dispatcher, so merely ensuring tables exist does not fetch public history. Additive indexes cover imported-comment status/order, OAuth category/expiry maintenance, outbox event lookups and unsettled order, event creation time and coordination attempt identities. Unsettled lookups explicitly select the partial index: the local runtime otherwise sometimes chooses the retained delivered-history primary key. The event-retention cutoff uses its time index while preserving the original maximum-sequence calculation and cleanup behavior. No stored columns, accepted replies, public result versions or authentication predicates change.

Hints use indexed durable target/receipt lookups before general pending work or GitHub admission. New hints rejected by the existing burst/hour/backoff/egress limits do not read public history or the general pending/recovery queue. An exact legacy conflict target can recover its previously hidden final without scanning historical conflicts or rewriting the accepted original reply. Already-pending hints return their durable pending receipt; normal reads still resolve them inside the existing GitHub cooldown, and a newly admitted predecessor hint still runs the general fixed-point pass after import. The pending cursor, eight rounds, pagination and dependency/conflict behavior remain intact. No recoverable row is marked complete or dropped to save reads.

The alarm scheduler selects each active subscription's oldest pending/failed occurrence through the unsettled index. A failed head contributes no pending delivery time, and a pending head contributes its actual backoff time. A later due occurrence cannot generate 50ms wakes ahead of that head. Eligible successors, other subscriptions, expiry, retention, missing transport configuration, transient retry limits and renewal/unsubscribe authority checks retain their existing behavior. New FIFO regressions verify deferred delivery, exact retry body, sequential acknowledgements and retention of a failed head and blocked successor.

Validation uses the pinned local workerd SQLite runtime with 5,000 fictional rows in each relevant table. Native SQL cursor rowsRead, rather than returned-row counts or elapsed time, measures warm steady-state costs. Fixture seeding and initial index migration are excluded from those measurements and must not be treated as free production work. The native regression also checks query plans, a complete 200-message page and cursor, rejected-hint status, unexpired history retention, and the deferred FIFO alarm. All fixtures are local; no cloud query, host activation, callback transport or private production session is used.

Larger follow-ups remain separate: the browser still reloads complete v1 history and private job pages; every public GET still checks legacy migration; Worker pre-import validation still fetches a page before the final read; repeated conflict recovery and unmatched outbox refill lack a durable examined/dirty cursor; the refill SELECT is still unbounded before its JavaScript enqueue cap. Those changes require their own recovery and compatibility design. This candidate does not claim a global per-day quota ceiling or complete elimination of read amplification.

Promotion requires independent review of this new candidate, explicit owner confirmation after the platform gate, approved-runtime source qualification for the actual integration commit, and subsequent authorized exact-head deployment pin/owner-gate qualification. Previously reviewed PR70/71/72 and their combined recovery bundle remain frozen. Initial production index construction consumes migration work and requires an approved window with sufficient quota; warm local costs do not establish that budget. Account attribution and outage status remain unverified because no authenticated cloud dashboard evidence is available.
